AI 模型策略

DeepSeek V4 API 尚未开放图片能力 — 双方案并存，按场景自动路由

背景与约束

核心矛盾

DeepSeek V4（2026年4月发布）在 App/Web 端已灰度上线"识图模式"，支持图片理解。
但 V4 API 仍然是纯文本接口 — 旧版 deepseek-chat / deepseek-reasoner 将于 2026年7月24日停用，新 API deepseek-v4-pro / deepseek-v4-flash 也尚未开放图片输入参数。

GCA 需要让 AI "看到"远程设备屏幕，但主力模型看不了图。
解决思路：方案 A 用两个模型配合（大脑+眼睛），方案 B 换一个能看图的多模态模型。

模型多模态 APIOpenClaw 原生上下文价格（输入/输出）开源定位
DeepSeek V4-Flash 无 是 1M 极低（GPT-5.5 的 1.55‰） MIT 推理大脑
DeepSeek V4-Pro 无 是 1M 低 MIT 深度推理
MiMo-V2.5 图+视频+音频 需配置 1M $1 / $3 per M MIT 全模态 Agent
MiniMax-M3 图+视频 是 1M $0.30 / $1.20 per M 闭源 多模态 Agent

方案 A：双模型架构

DeepSeek V4 做大脑（推理+工具调用），视觉模型做眼睛（截图转结构化文本）。两步分离，各司其职。

方案 A 推荐 — 性价比最优

角色模型职责API价格
大脑 DeepSeek V4-Flash 对话推理、工具调用、决策 OpenAI 兼容 极低
眼睛 MiMo-V2.5 备选: MiniMax-M3 截图理解，输出结构化描述 OpenAI 兼容 $1/$3 per M

工作流程

用户指令："帮我看下服务器桌面上有什么文件" Step 1 screen_capture("cloud-svr") │ ▼ WebP 截图 (~30KB, 512px) Step 2 截图 → 视觉模型 (MiMo-V2.5) │ prompt: "描述屏幕内容，列出所有可见元素" ▼ 返回结构化文本 Step 3 结构化文本 + 用户指令 → DeepSeek V4-Flash │ "桌面上有 3 个 PDF: report.pdf, invoice.pdf, spec.pdf" │ 推理: 用户可能想看文件列表 ▼ 决策: 调用 file_list("cloud-svr", "~/Desktop") Step 4 file_list 执行 → 返回结果 → DeepSeek 组织回复

关键优化：视觉描述缓存

屏幕没变就不重新理解。screen_capture 返回图片 hash，与上次对比：
- hash 相同 → 直接用缓存的视觉描述，跳过 Step 2（省 1 次 API 调用）
- hash 不同 → 重新调用视觉模型

典型场景：AI 正在执行多步操作，中间多次截图，但屏幕内容未变 → 只需 1 次视觉理解。

优点
  • DeepSeek V4-Flash 推理极强（Codeforces 3206），Agent 能力榜首
  • 总成本极低 — V4-Flash 价格碾压级，视觉模型只在看图时调用
  • 视觉模型可独立替换 — MiMo/MiniMax/Qwen-VL 随时切换
  • 视觉描述可缓存 — 屏幕没变不重新理解
  • 纯文本任务（命令行/系统管理）完全不调视觉模型，零额外成本
缺点
  • 看图时需 2 次 API 调用，延迟 +1-2s
  • 文本转换有信息损失 — 复杂图像/动画/颜色难以完整描述
  • 需要维护两个模型的 API Key 和配置
  • 视觉模型理解质量直接影响 AI 决策质量

OpenClaw 配置

~/.openclaw/openclaw.json — 方案 A 
{
  // 主模型 — 推理大脑
  "agent": {
    "model": "deepseek/deepseek-v4-flash",
    "apiKey": "${DEEPSEEK_API_KEY}"
  },

  // 视觉模型 — 眼睛（通过 MCP Tool 内部调用，非 OpenClaw 直配）
  // 配置在 GCA MCP Server 的环境变量中
  "mcpServers": {
    "home-pc": {
      "url": "http://192.168.1.100:3001/sse",
      "env": {
        "VISION_MODEL": "mimo-v2.5",
        "VISION_API_KEY": "${MIMO_API_KEY}",
        "VISION_BASE_URL": "https://api.xiaomimimo.com/v1"
      }
    }
  }
}

方案 B：多模态单模型架构

直接用多模态模型，一步到位看图+推理+决策。少一次 API 调用，无信息损失。

方案 B GUI 操控场景更优

角色模型（二选一）职责API价格
大脑+眼睛 MiMo-V2.5 推荐 直接看图 + 推理 + 工具调用 OpenAI 兼容 $1/$3 per M
大脑+眼睛 MiniMax-M3 同上，OpenClaw 原生支持 OpenAI/Anthropic $0.30/$1.20 per M

工作流程

用户指令："帮我看下服务器桌面上有什么文件" Step 1 screen_capture("cloud-svr") │ ▼ WebP 截图 (~30KB, 512px) Step 2 截图 + 用户指令 → 多模态模型 (MiMo-V2.5) │ 模型直接"看"屏幕: │ "桌面上有 3 个 PDF: report.pdf, invoice.pdf, spec.pdf" │ 推理: 用户可能想看文件列表 ▼ 决策: 调用 file_list("cloud-svr", "~/Desktop") Step 3 file_list 执行 → 返回结果 → 模型组织回复
优点
  • 单次 API 调用，延迟低
  • 无信息损失 — 原生视觉理解，能看到颜色/布局/动画
  • GUI 操控更精准 — 能直接看到按钮位置、输入框状态
  • 配置简单 — 只需一个模型 API Key
  • MiMo-V2.5 原生 Agent 能力 + Browser Use，天生适合操控场景
缺点
  • 纯文本推理能力可能弱于 DeepSeek V4
  • 每次调用都含图片 token，成本高于方案 A 的纯文本调用
  • MiMo 需在 OpenClaw 中自定义 Provider（OpenAI 兼容 endpoint）
  • MiniMax 闭源，长期依赖第三方

推荐：双方案并存，按场景自动路由

不是二选一，而是共存

GCA 的 MCP Server 同时支持两套屏幕理解路径。
OpenClaw AI Agent 根据任务类型自动选择调用哪个 Tool：

任务类型走哪个方案调用链路原因
命令行 / 系统管理 方案 A DeepSeek V4-Flash 直接处理 不需要看图，纯文本推理，V4-Flash 最强最便宜
文件操作 / 日志查看 方案 A DeepSeek V4-Flash 直接处理 同上，结构化数据 V4 足够
GUI 操作 / 按钮点击 方案 B 多模态模型直接看图 需要看屏幕布局，判断按钮位置和状态
远程桌面操控 方案 B 多模态模型看图 + 推理 需要视觉判断，颜色/图标/动画
故障排查（看日志+看屏幕） 方案 A ui_tree + DeepSeek V4 结构化 UI 信息足够，不需要视觉理解
网页操作 方案 B 多模态看图 / browser_act 需要看页面渲染效果

Agent 决策路径

不是问用户"走哪个方案"，而是由 openclaw.json 中配置的主模型决定可用路径。
Agent 收到用户指令后，主模型自主分析意图、选择工具、执行操作，全程零人工介入。

关键：视觉路径由配置决定，不由指令决定

同一条指令"帮我点那个蓝色按钮"，在两种配置下走不同路径：

配置主模型Agent 调用链谁"看"屏幕
方案 A DeepSeek V4-Flash screen_capture → MCP Server 内部调 MiMo → 返回结构化文本 → V4-Flash 推理 → remote_input MiMo（眼睛）
V4-Flash（大脑）
方案 B MiMo-V2.5 screen_capture → image content 直接返回 → MiMo 看图 + 推理 → remote_input MiMo（眼睛+大脑合一）

Agent 不需要知道"我该走方案 A 还是 B"——它只是调用 screen_capture 工具，
MCP Server 根据自身配置决定返回 image（方案 B）还是调用视觉模型转文本（方案 A）。
对 Agent 来说，无论哪个方案，它调用的都是同一个 Tool。

屏幕截图优化（两方案共用）

从 base64 JPEG 到 WebP MCP image — 效率提升 10 倍+

旧方案：screenshot 返回 base64 JPEG（1920x1080 ~400KB）
新方案：screen_capture 返回 MCP image content type（WebP 512px ~30KB）

维度旧方案 (screenshot)新方案 (screen_capture)提升
格式 JPEG base64 WebP（MCP image content type） 原生支持
分辨率 1920x1080 原始 512px 自适应（长边） 按需缩放
体积 ~400KB ~30KB 13x 压缩
Token 消耗 ~1200 tokens（base64 编码膨胀） ~300 tokens（WebP 直接传递） 4x 节省
变化检测 无（每次全量传输） hash 对比，屏幕未变跳过 省 API 调用
区域截图 不支持 支持 region 参数（只截指定区域） 更精准

screen_capture 工具定义

MCP Tool Schema 
{
  "name": "screen_capture",
  "description": "截取远程设备屏幕画面，返回 WebP 格式图片（MCP image content type）",
  "inputSchema": {
    "type": "object",
    "properties": {
      "device": { "type": "string", "description": "目标设备 ID" },
      "display": { "type": "number", "default": 0, "description": "显示器编号（多屏时指定）" },
      "maxWidth": { "type": "number", "default": 512, "description": "最大宽度（px），控制图片大小" },
      "quality": { "type": "number", "default": 75, "description": "WebP 质量 (1-100)" },
      "region": {
        "type": "object",
        "description": "只截取指定区域（不填则全屏）",
        "properties": {
          "x": { "type": "number" },
          "y": { "type": "number" },
          "width": { "type": "number" },
          "height": { "type": "number" }
        }
      }
    },
    "required": ["device"]
  }
}

ui_tree — 结构化 UI 元素树（无 API 成本）

不调任何模型，本地 Accessibility API 提取

ui_tree 通过操作系统 Accessibility API（Windows UIAutomation / macOS AXUIElement / Linux AT-SPI）
直接获取当前屏幕的 UI 元素树：窗口标题、按钮文本、输入框位置、列表项等。
零 API 成本，毫秒级响应。适合方案 A 中替代视觉模型做简单的屏幕理解。

维度ui_treescreen_capture + 视觉模型
API 成本 免费 每次调用付费
延迟 <100ms 1-3s
信息类型 结构化（坐标+文本+类型+状态） 自然语言描述
视觉信息 无（看不到颜色/图标/图片） 完整
适用场景 原生应用 UI 操作、表单填写、菜单导航 网页/图片/非标准 UI、需要视觉判断

场景→工具链映射

下表不是 Agent 运行时的决策树——所有路由都是主模型根据指令语义自主判断的。
这里只是说明：不同类型的指令，主模型"倾向于"走哪条路径，以及对应的成本和延迟。

用户指令示例主模型判断调用工具视觉路径成本延迟

"桌面上有哪些文件" 结构化 UI 即可 ui_tree() 免费(本地) 免费 ~0.5s
"帮我看下日志里的报错" 文件读取，纯文本 file_read() 不需要 最低 ~1s

"看下这个网页为什么显示异常" 需要视觉判断 screen_capture() → 分析 方案A: MiMo 转文本
方案B: 直接看图		 中 A:~3s / B:~2s
"检查应用是否正常加载" 需要视觉验证 screen_capture() → 判断 方案A: MiMo 转文本
方案B: 直接看图		 中 A:~3s / B:~2s

核心原则

1. 主模型决定调什么工具——根据指令语义和 Tool 描述自主选择
2. 配置决定视觉路径——方案 A 还是 B 在 openclaw.json 里定死，运行时自动走
3. Agent 无感知——无论哪个方案，Agent 调用的都是 screen_capture，MCP Server 内部处理差异
4. 纯文本任务零成本——命令行/文件/系统信息类任务不触发任何视觉路径，V4-Flash 直接处理
